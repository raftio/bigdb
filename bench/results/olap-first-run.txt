# big analytical benchmark

200000 records, dense ids, 256 categories, 20 countries, amounts under 1048576.
Questions: `amount >= 786432`, country `n07`, active `true`, top 10.

Every answer below was checked against a ground truth computed without any engine; a wrong answer aborts the run rather than being printed. Query timings are medians of 3; the load is a single shot.

The load row excludes the settle that follows it - DuckDB's `CHECKPOINT`, ClickHouse's `OPTIMIZE ... FINAL` - the same split the storage report uses, where a checkpoint is charged to the size that is measured after it rather than to the write that preceded it. An engine that defers work therefore shows a cheaper load here and pays for it in the size row.

`big` is asked in its own query language and every other engine in SQL or PQL, so each one plans its own question rather than being handed a loop to run.
